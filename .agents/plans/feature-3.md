# Feature 3: `implement` — generate interface methods on union variants

## Status: Brainstorming

## The pattern

In `agentapis/api/responses/stream.go`, there are **131 lines** of pure boilerplate:

```go
type StreamEvent interface {
    responsesStreamEvent()
    EventType() string
}

// 53× marker methods
func (e *ResponseCreatedEvent) responsesStreamEvent() {}
func (e *ResponseInProgressEvent) responsesStreamEvent() {}
// ...

// 53× accessor methods
func (e *ResponseCreatedEvent) EventType() string { return string(e.Type) }
func (e *ResponseInProgressEvent) EventType() string { return string(e.Type) }
// ...
```

Every single line follows a mechanical pattern. The interface has two methods:
1. A **marker method** (already generated by compschema's `uniongen`)
2. An **accessor method** that returns `string(e.Type)` — same body on every variant

compschema already generates #1. The question is: how to also generate #2, and more generally, how to let users add **custom methods to all variants** of a union.

## What this really is

Zooming out, this is a broader pattern than just events:

- **Union variants sharing a method** — all variants of a discriminated union can return their discriminator value via a common method
- **Accessor generation** — a field exists on every variant, generate a getter that returns it through a shared interface
- **Protocol conformance** — make all variants implement an external interface (not just the sealed marker)

## Design options

### Option A: `--methods` on union config

Add method generation as a union-level config:

```yaml
implement:
  - union: ResponseStreamEvent
    interface: StreamEvent
    methods:
      - name: EventType
        returns: string
        body: "return string(e.Type)"
```

**Pros:** Fully explicit, handles any method body
**Cons:** Hardcoded Go code in YAML config — fragile, hard to validate, essentially a template engine

### Option B: Auto-detect from discriminator field

compschema already knows `ResponseStreamEvent` is discriminated by `"type"`. Every variant has a `Type` field with a const value. We can **automatically** generate:

```go
func (e *ResponseCreatedEvent) EventType() string { return string(e.Type) }
```

The pattern: for every discriminated union, generate a method that returns the discriminator field value as `string`.

```yaml
implement:
  - union: ResponseStreamEvent
    discriminator_accessor: EventType  # method name, auto-generates body
```

Or even without config — just always generate it for discriminated unions:

```go
// Auto-generated for every discriminated union:
// Interface method: {DiscriminatorField}Value() string
func (e *ResponseCreatedEvent) TypeValue() string { return string(e.Type) }
```

**Pros:** Zero config for the common case, leverages existing IR knowledge
**Cons:** Only handles the discriminator field pattern, not arbitrary methods

### Option C: Field accessor methods (generalized)

Generalize: for any field that exists on **all variants** of a union, optionally generate an accessor method on each variant that the interface can require:

```yaml
implement:
  - union: ResponseStreamEvent
    accessors:
      - field: type          # JSON field name
        method: EventType    # Go method name
        returns: string      # return type (defaults to field's Go type)
```

This is a superset of Option B. The discriminator field is just one case — you could also generate accessors for `sequence_number` if all variants have it.

**Pros:** General, handles both discriminator and shared fields
**Cons:** Still config-driven, but minimal config

### Option D: Auto-generate from shared fields (zero config)

Detect fields that exist on **all variants** of a union and auto-generate accessor methods. No config needed.

For `ResponseStreamEvent`:
- All 53 variants have a `Type` field → generate `TypeValue() string`
- All 53 variants have a `SequenceNumber` field → generate `SequenceNumberValue() int`

The interface automatically includes these methods:

```go
type ResponseStreamEvent interface {
    isResponseStreamEvent()
    TypeValue() string
    SequenceNumberValue() int
}
```

**Pros:** True zero config
**Cons:** May generate unwanted methods, naming might be awkward (`TypeValue` vs `EventType`), can't customize method names, might bloat interfaces

### Option E: Hybrid — auto-detect + config override

Auto-detect shared fields on discriminated unions. By default, generate a discriminator accessor with a sensible name. Allow config to customize:

```yaml
implement:
  - union: ResponseStreamEvent
    rename: StreamEvent              # optional: rename the interface
    discriminator_method: EventType  # optional: customize method name (default: {Field}Value)
    accessors:                       # optional: additional shared field accessors
      - field: sequence_number
        method: SeqNum
```

Without any config, discriminated unions auto-get `{Field}Value() string`.

## Recommendation: Option C (field accessors) with auto-discriminator

Option C is the sweet spot:

1. **Discriminated unions auto-get a discriminator accessor** — always generated, default name `{DiscriminatorField}Value()`, override with config
2. **Additional accessors are config-driven** — explicit, predictable, handles the `sequence_number` case
3. **The interface includes the accessor methods** — not just the marker

This covers the real use case (stream.go) with minimal config, while being general enough for other patterns.

### What gets generated (default, zero config)

For every discriminated union, auto-generate:

```go
// Before (today):
type ResponseStreamEvent interface {
    isResponseStreamEvent()
}

// After (auto):
type ResponseStreamEvent interface {
    isResponseStreamEvent()
    TypeValue() string   // auto-generated for discriminator field "type"
}

// + on every variant:
func (e *ResponseCreatedEvent) TypeValue() string { return string(e.Type) }
```

### What gets generated (with config)

```yaml
implement:
  - union: ResponseStreamEvent
    discriminator_method: EventType  # rename TypeValue → EventType
```

```go
type ResponseStreamEvent interface {
    isResponseStreamEvent()
    EventType() string
}

func (e *ResponseCreatedEvent) EventType() string { return string(e.Type) }
```

### What about interface renaming?

The `stream.go` uses `StreamEvent` instead of `ResponseStreamEvent`. This is already handled by `--rename` on import:

```yaml
rename:
  ResponseStreamEvent: StreamEvent
```

No new feature needed for that.

## How it connects to existing features

| Feature | What it does | Status |
|---------|-------------|--------|
| **Union generation** (`uniongen`) | Sealed interface + marker methods + `UnmarshalX` | ✅ Exists |
| **Discriminator detection** | Auto-detect discriminator field from const/enum values | ✅ Exists |
| **`DecodeX` + `XAs`** | Type-safe decode + variant extraction | ✅ Exists |
| **Constructors** (feature-2) | `NewT()` auto-fills const fields | Planned |
| **Embed** (feature-1) | Extract shared fields (type, sequence_number) into `EventMeta` | Planned |
| **Implement** (this feature) | Generate accessor methods on all variants | **This proposal** |

Note: `embed` (feature-1) and `implement` (this feature) solve **different problems** for the same types:

- `embed` extracts shared *fields* into a base struct → structural refactoring
- `implement` adds shared *methods* to all variants → behavioral conformance

With `embed` + `external: true`, EventMeta provides the methods via hand-written code. With `implement`, compschema generates the methods directly — no hand-written code at all. **They're alternatives, not complements.** For the event case, `implement` is simpler (no embed type needed) but less flexible (can't add custom logic like `Error()` on `ResponseErrorEvent`).

The pragmatic approach: use `implement` for the common case (discriminator accessor), use `embed external: true` when you need custom method logic.

## Implementation sketch

### IR changes

Add to `ir.Type` (KindUnion):

```go
type Type struct {
    // ... existing ...
    
    // KindUnion — accessor methods to generate on all variants
    Accessors []Accessor
}

type Accessor struct {
    Method     string // Go method name (e.g. "EventType")
    Field      string // JSON field name to access (e.g. "type")
    ReturnType string // Go return type (e.g. "string")
}
```

### Config

```go
type ImplementRule struct {
    Union               string   `json:"union" yaml:"union"`
    DiscriminatorMethod string   `json:"discriminator_method,omitempty" yaml:"discriminator_method,omitempty"`
    Accessors           []AccessorConfig `json:"accessors,omitempty" yaml:"accessors,omitempty"`
}

type AccessorConfig struct {
    Field  string `json:"field" yaml:"field"`
    Method string `json:"method" yaml:"method"`
}
```

### Codegen (in uniongen)

After emitting marker methods, for each accessor:

```go
for _, variant := range t.Variants {
    for _, acc := range t.Accessors {
        // Find the field on the variant
        field := findField(variant, acc.Field)
        fmt.Fprintf(b, "func (e *%s) %s() %s { return %s(e.%s) }\n",
            variantName, acc.Method, acc.ReturnType,
            acc.ReturnType, fieldGoName)
    }
}
```

### Auto-discriminator (default behavior)

In `EmitUnion`, if `t.Discriminator != ""` and no explicit accessor config:

```go
// Auto-generate discriminator accessor
defaultAccessor := Accessor{
    Method:     toGoName(t.Discriminator) + "Value",
    Field:      t.Discriminator,
    ReturnType: "string",
}
```

## Open questions

1. **Should the accessor method go on the union interface?** If yes, the interface changes shape based on config. If no, it's just methods on the variants but no interface guarantee. **Leaning yes** — the whole point is interface conformance.

2. **How to handle the `Error()` case?** `ResponseErrorEvent` implements `error` with custom logic. This can't be auto-generated. Answer: out of scope — hand-write it in a separate file. `implement` handles the mechanical pattern, custom methods stay manual.

3. **What if a variant doesn't have the accessor field?** Skip that variant and log a warning. The method won't be on the interface (or the interface won't include it). Alternative: require all variants to have the field, error if not.

4. **`embed` vs `implement` for the event case?** Both solve it differently. `embed` is structural (base struct with methods), `implement` is behavioral (generate methods directly). They could coexist — `embed` for field dedup, `implement` for method generation on non-embedded unions.
